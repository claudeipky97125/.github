<h2>二、环境六项：时区、语言、UA、分辨率、字体、WebRTC</h2>

<h3>UI 语言和请求头语言为什么要一起看</h3>

<p>时区排第一，因为它是最容易被交叉验证的一项。语言其次，注意区分浏览器 UI 语言和 Accept-Language 请求头，两者最好一致。UA 不必刻意伪装成某个具体版本，保持与浏览器实际版本一致即可，改得越花越容易露馅。</p>

<h3>分辨率和字体为什么也算参数</h3>

<p>两者共同决定页面渲染出的指纹特征。新装的系统常用默认字体集，而某些地区的系统会带上区域字体，这与出口地区矛盾时会被注意到。做法不是去伪造，而是让系统安装与所选地区匹配的语言包，保持自然。</p>

<p>WebRTC 这一项建议直接关闭非代理 UDP，避免本地内网地址泄露。Chrome 可用策略文件配置，Firefox 在 about:config 里把媒体相关项设为禁用。改完在检测页确认没有 192.168 段出现。</p>

<h2>三、网络五项：出口、DNS、MTU、超时、重试</h2>

<h3>超时设短了会连带影响什么</h3>

<p>出口是主参数，其余四项是配套。DNS 建议走代理解析，避免本地解析器泄露真实位置；MTU 保持默认 1500，跨境链路出现分片问题时再下调到 1400 试；超时按场景设，网页 15 秒、接口 60 秒、流式输出要更长；重试最多两次，且必须带退避。</p>

<h2>四、账号四项：资料、邮箱、验证方式、支付</h2>

<p>资料要填真实且自洽的信息：姓名拼写、地区、时区、语言四项互相吻合。邮箱建议用常见服务商，域名过于冷门的邮箱在注册环节更容易被要求额外验证。验证方式优先手机号或验证器应用，邮箱验证的恢复路径更脆弱。</p>

<p>支付这一项最敏感。发卡地、账单地址、订阅地区三者最好同国，跨地区组合容易在扣费环节失败。测试支付时用最小金额，别用来源不明的方式，也不要频繁更换卡。这里补充一句：一个真实的人对应一个真实账号，批量注册既违反多数平台条款，也会让上述所有参数配置失去意义。</p>

<h3>什么时候允许改参数</h3>

<p>只有两种情况：搬迁导致时区真实变化，或者服务商节点下线必须换出口。除此之外的改动都应该先问一句"改了能解决什么"，答不上来就别动。参数稳定本身就是一种信号。</p>

<h2>常见问答</h2>

<h3>时区必须和出口城市完全一致吗？</h3>

<p>答：同一时区即可，不必精确到城市。跨时区的国家要注意，比如美国西岸与东岸差三小时，出口在洛杉矶却用纽约时区就会矛盾。</p>

<h3>UA 需要跟着代理地区改吗？</h3>

<p>答：不需要。UA 反映的是浏览器版本和系统，与地理位置无关。刻意改成别的地区版本反而与系统语言、字体不匹配，得不偿失。</p>

<h3>DNS 一定要走代理吗？</h3>

<p>答：建议走。本地 DNS 会把解析请求暴露给本地运营商，也可能把域名解析到就近节点，导致实际访问路径与出口地区不符。用代理解析或指定同区解析器都可以。</p>

<h3>参数配好之后还会出问题吗？</h3>

<p>答：会。参数只保证环境自洽，不保证账号行为正常。高频操作、异常时间登录、支付失败次数过多，都会独立触发验证，这些不在参数表的覆盖范围内。</p>
